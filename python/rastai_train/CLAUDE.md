# python/rastai_train: the trainer and its recipes

Read the root `CLAUDE.md` and `python/CLAUDE.md` first. The layout is `docs/architecture/layout/python.md` §5; the run, checkpoint and resume flows are `docs/architecture/flows/training-evaluation.md` §4 and §5.

- **What is here (M1-38).** `context.py` (`build_training_context`, `TrainingSettings`, `CheckpointPolicy`, `TrainingProgress`), `loop.py` (`train`, `prepare_run`, `train_from_current_step`, `optimizer_step`, `preempt_at_step_boundary`, `TrainingOutcome`), `optimizer.py` (AdamW, the warmup-cosine schedule, state ↔ named tensors), `checkpoints.py` (write, find, keep, fall back), `resume.py` (resume.json, rng.safetensors, `load_resume_state`), `errors.py` (`TrainError`) and `recipes/` (`ClassificationRecipe`, `FIRST_PARTY_RECIPES`, `register_first_party`). Losses, adaptation, anchors, the other recipes, the capability matrix, multi-GPU and export land in their build steps (§5.9).
- **The loop owns backward, the optimizer, clipping, the schedule, metrics and checkpoints.** A recipe returns a loss and its metrics (`StepResult`) and nothing else, so every recipe gets the same accumulation, cadence and flag handling. Flags are read only at a step boundary; `preempt_requested` first, because only SIGTERM has a deadline. The SIGTERM checkpoint skips the validation pass: the preemption budget times only the write, and a validation pass over a large split could outlast a spot notice.
- **The loop never writes the final run state.** It writes `run.state_changed running` at its start, `run.metrics` and `checkpoint.saved`; `rastai_worker/diagnostics.py` writes the final state and picks the exit code from the `JobControl` flags (75 after SIGTERM). `train.preempted` and `checkpoint.resumed` are M5 events: don't emit them before their contract lands (a worker refuses an event type it doesn't know).
- **No pickle, ever** (ADR-0024). Weights, optimizer state and RNG states are safetensors through `rastai_models`' writer and reader; resume.json is `rastai.resume/1` written and read through the `rastai_formats` wheel. Never `torch.save`, `torch.load` or an optimizer's `state_dict()` on disk: optimizer state is saved by parameter name (`<graph path>.<state>`), never by index.
- **A checkpoint exists only after its rename.** Files go into `step-NNNNNNNN.partial/`, each synced, the folder synced, then renamed and the parent synced; `checkpoint.saved` is emitted after that. Nothing here ever returns a `.partial` folder (`list_complete_checkpoints` matches `step-` and eight digits exactly). A full disk removes the `.partial` folder and raises `RRS-T2001`.
- **The resume contract is bit for bit on the CPU.** A resumed run must give the same loss at every step, the same weights, optimizer state and generator state as an uninterrupted one (`tests/test_resume.py`). That holds because: the order of an epoch is a pure function of (shuffle seed, epoch), so the loader's position is two numbers; the RNG is restored after `recipe.prepare` and before the first batch; validation puts the generators back when it ends, so checkpoint cadence can't move the training stream; and `deterministic` turns on torch's deterministic kernels. Anything new that draws randomness or keeps state across steps must join resume.json or rng.safetensors, with a case in that test.
- **Codes.** Damaged checkpoint files are `RRS-T2002` (the caller tries the next older checkpoint; the newer ones it passed stay on disk for inspection, and their steps, in `TrainingProgress.skipped_checkpoint_steps`, are left out of the run's latest, best and keep_last until it writes that step again); a checkpoint of another run, dataset, split, schedule, design or label set is `RRS-T2005`; none left is `RRS-T2004`; three non-finite steps in a row `RRS-T3001`; rows a recipe can't use `RRS-T0003`; a design that doesn't fit the recipe `RRS-T0005`. A design the wheel refuses keeps the wheel's code (`train_error_from_refusal`). Out-of-range settings are a bug in the caller: `ValueError`.
- **Settings.** `CheckpointPolicy` holds the generated `SettingsCheckpoint` (no second copy of the `training.checkpoint` shape); build it with `checkpoint_policy`, which fills what the settings leave out. `deterministic` defaults on: on a GPU, cuBLAS refuses deterministic matmuls unless `CUBLAS_WORKSPACE_CONFIG` (`:4096:8`) is in the environment before CUDA starts, so the train job (M1-46) sets it for GPU runs.
- **Memory defaults (spike, layout §5.3)**, for the recipes that need them: loss only at answer positions, LoRA masters in float32 with bf16 compute, gradient checkpointing on. They arrive resolved in the settings and join with `losses.py`, `adaptation.py` and the SFT recipe (M5); TextCNN classification needs none of them and trains in float32 on the CPU.
- **Boundaries** (layout §5.6): never imports `rastai_worker`, `rastai_rl` or a plugin; never writes outside the run folder and `cache_folder`; never decides placement or memory caps.
- Tests are in `tests/test_<module>.py`, CPU only, and run in `test-python-portable` too. Each test file is self-contained: a `conftest.py` under a package's `tests/` would shadow the package in pytest's importlib mode (see `python/conftest.py`). Every test that builds a context restores torch's global generator and deterministic flag afterwards.
