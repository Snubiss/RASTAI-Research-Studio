- **M1-39 (contract):** A code for a second event-log writer, and the paths that carry it. `rastai_worker`'s `EventLogWriter` takes an exclusive `flock` on `events.log`, so a relaunch racing a live job can't interleave frames with it (7.1; python layout 7.5). The layout named the refusal only as `RRS-J3xxx`, and no code covered it: `RRS-J2001` ("Worker couldn't start") would tell the user to reinstall the environment, which never helps here. `RRS-J3006` joins the reattach range, 3000–3999 (10.3): another worker is already writing this run's event log, and the second job stops before writing anything. The worker that loses the lock must not write the log, so the code can't reach the node through a logged diagnostic or exit 1 (which would read as `RRS-J1004`): a new worker exit code, `5` `EXIT_EVENT_LOG_LOCKED`, carries it (9.1; 15.2's `rastai_worker` row; python layout 7.2 and 7.5; platform flow 5.4 and 5.5; node layout 7.4). The worker prints the diagnostic to `stderr.log` (opened for append, so the running copy's lines stay), touches neither `events.log` nor `events.log.reserve`, and exits 5 before `Register`; the node fails the job `starting` → `failed` with `RRS-J3006` and the stderr tail. What happens to the refused job: the node checks first and refuses a `StartJob` for a run that already has a live job (its own job table, or a `job.json` with no `final_state` whose pid, boot id and start ticks are alive) with `RRS-J3006`, `queued` → `failed`, before it writes `job.json` or anything else into the run folder. The check and the reservation are one step: under one hold of the `JobTable` lock (`NodeState.jobs`), the node looks for a live job of the run and enters the new job as the run's live job, so two `StartJob`s for one run can't both pass, and only an admitted job ever gets a `job.json`; the reservation ends only after the job's terminal `job.json` is written (9.1). Exit 5 is the backstop for a writer the node doesn't know is alive (for example a worker started by hand, or one whose `job.json` was lost or damaged). That writer had no live `job.json`, so the `job.json` in the run folder is the refused job's own, written after its admission, and the node finalizes it with `final_state` `failed` as on any terminal state; it never writes a terminal `job.json` over another live job's, and the final state keeps a node restart from reading the running copy's log as this job's outcome. Either way the running copy keeps going: the node sends it no signal and takes none of its leases (a refusal before spawn also leaves its `job.json` untouched), and neither the node nor the daemon takes an outcome for the refused job from the run's log or writes the run's state for it, as the catalog's basic text ("Rastai didn't start a second copy of it") promises.
- **M1-39:** The Python event-log writer and payload conversion. `rastai_worker` lands with `event_log.py`, `event_payloads.py` and `errors.py`, so it loses its (M1) marker (2.2, 15.2); its names not built yet carry the milestone of their task (15.2). 15.2 registers the code names: `EventLogWriter`'s methods, `encode_frame`, `find_end_of_whole_frames`, `current_unix_ms`, `payload_from_dict`, `WORKER_EVENT_PAYLOAD_FIELDS`, `encode_message`, `decode_event_record` and `WorkerError`. A frame's bytes are the same from either writer: Python's protobuf runtime (upb) writes a map entry's default key and value and orders a key before its own prefix ("ab" before "a"), where prost leaves defaults out and writes keys in byte order, so a metric of 0.0 would have changed the frame and its CRC. `encode_message` writes prost's form, checked against every frame-body proto golden and by the new fixture `from_python.log`, which the Rust reader reads frame for frame and the Rust writer writes byte for byte (`crates/rastai-store/tests/python_log_compat.rs`, 15.8). The writer's open applies the Rust reader's verdicts of 7.1, ported line for line, so a torn tail is cut and corruption refused the same way in both languages. A second writer is refused with `RRS-J3006` before it reads or writes the log or `events.log.reserve` (M1-39 (contract); 9.1, one live job per run), and its exit with `EXIT_EVENT_LOG_LOCKED` (5) arrives with the job process (M1-40); the log's own errors keep the store's codes (`RRS-S0006`, `S2002`, `S2003`, `S3002`, `S3005`), carried by `WorkerError`. `pause_for_full_disk` arrives with the job process (M1-40); the reserve file is written and deleted here. `python/envs/cpu` installs `rastai-worker` from its folder, and `schemas/names.json` lists the package (12.6).
