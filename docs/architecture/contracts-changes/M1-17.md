- **M1-17 (contract):** The step-1 documents. `rastai.run_record/1`, `rastai.resume/1`, `rastai.settings/1`, `rastai.project/1`, `rastai.lock/1`, `rastai.plugin/1` and `rastai.theme/1` land as structs with their descriptions, schemas and generated JavaScript and Python types, so their 5.2 rows and the M1 sections of 11.2 lose their (M1) markers, and 15.1 registers their code names and layer 3's. Shapes this PR settles: a chain step is `{step_name, child_run_id, command_id, arguments_json, optional}` (5.2); `contributes` has all 31 keys of 5.5, with typed entries for `commands`, `sections`, `panels`, `settings_pages`, `themes` and `event_handlers` and JSON objects for the rest until their extension point is built (5.2); in a theme every token group is required and each color role optional (5.2, 5.6); a settings file holds only the keys its layer sets and never `null` (11.1). One new code, `RRS-E2006` (a value isn't in its required form): layer 3 reports a theme color that isn't `#rrggbb`, a malformed plugin or command id in a manifest and a project's default node with it, where the first draft would have borrowed layer 2's `RRS-E1004` (10.3). A manifest's reserved plugin id is `RRS-P0002`, a command outside its namespace or an event handler naming another plugin's command `RRS-P0004`, and a command listed twice `RRS-E2005`, as the registry already does (M1-21). The id rules of 6.1 (`is_plugin_id`, `is_command_id`, `CORE_AREAS`) move from rastai-core's `naming.rs` into `rastai-formats`, which sits below it, so the manifest check and the registry keep one implementation; `rastai-formats` becomes a regular dependency of `rastai-core` (2.1 already listed it). The platform flow's project section no longer lists `data_policy` in `project.json` (11.1 holds it).
