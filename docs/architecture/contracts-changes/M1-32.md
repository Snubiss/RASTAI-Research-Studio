- **M1-32:** The plugin host. `rastai-server` gains `plugin_host/` (`capabilities.rs`, `discovery.rs`, `load.rs`, `contributions.rs`, `lifecycle.rs`) and `commands/handlers/plugin.rs`, so `HostCapability`, `FirstPartyCapability`, `HOST_CAPABILITIES`, `FIRST_PARTY_CAPABILITIES`, `negotiate_capabilities`, `NegotiationResult`, `LoadedPlugin` and `PluginSource` lose their (M1) markers in 15.1, which also registers `CapabilityStatus`, `AvailableCapability`, `available_capabilities`, `state_after_negotiation`, `negotiation_diagnostics`, `PluginHost` (the `Server` field `plugins`), `discover_plugins`, `load_all_plugins`, `load_plugin`, `unload_plugin`, `disable_plugin` and `check_module_isolation`. The capability table is 5.5's 31 rows as data: `ui.theme@1`, `ui.icon_set@1`, `ui.macro@1` and `inference.chat_template@1` (M8), and `ui.locale@1` and `assistant.skill@1` (Phase 2), are unsupported and refused with `RRS-P1002`; `data.source@1`, `inference.tokenizer@1`, `inference.adapter@1` and `compute.target@1` are experimental (`RRS-P1003` without `plugins.experimental_apis`); a used contribution key whose capability isn't required is `RRS-P0006`; an `engines.rastai` range that excludes `PLUGIN_API_VERSION`, or doesn't parse, is `RRS-P1001`; a dependency not enabled in range is `RRS-P3001`, and so is a dependency cycle. At startup the daemon discovers installed and preinstalled plugins (a `plugins` row and its folder) and the folders of `plugins.dev_paths` (granted what their manifests ask for, since only the owner names them), then loads first-party plugins first and the rest in dependency order. A manifest that can't be read is `failed` with `RRS-P0001` and its `RRS-E` details, its id taken from the folder's name; one with layer-3 problems (`RRS-P0002`, `RRS-P0004`) is `incompatible`; the daemon keeps running either way. An enabled plugin's commands are registered with its id as their section, its version as `since_version` and, when the manifest names no scope, `plugin:<plugin_id>`; a command whose scope the plugin doesn't hold (its granted `commands:[scopes]` and its own scope; another plugin's `plugin:` scope is never granted) is refused with `RRS-C1005` and the rest load. A plugin that leaves `enabled` loses its commands at once; disabling a plugin checks every other enabled plugin again, so a lens plugin loses `psychology.lens@1` with Psychology. `execute_command` now takes `acting_plugin_id`'s grant from the host (nothing for a plugin that isn't enabled) and answers `RRS-C0003` for a plugin command whose plugin isn't enabled, followed by the plugin's own diagnostics. `plugin.list` is built. Each state change is a `plugin.state_changed` record with its reason as the diagnostic, logged and kept in `PluginHost.state_changes` until the daemon log and the bus take it (M1-28); an installed plugin's state is saved in its `plugins` row. Unpacking the archives shipped under the install prefix (M4-E02), plugin catalogs (`RuntimeCatalog`, M8), `types.json` schemas (M4) and starting modules (M4, through `check_module_isolation`) come later. No new codes, commands, events, tables or settings.
- **M1-32:** Two transitions join 9.7 and rastai-core's `PLUGIN_TRANSITIONS`: installed → incompatible and installed → awaiting_trust. Every start checks an installed plugin again (platform flow 7.3 draws the load of an installed plugin ending `incompatible`), and a dev folder counts as installed.
- **M1-32:** Owner-only settings keys (11.1; threat model R27, now closed): `nodes.ssh_binary`, `plugins.dev_paths`, `sandbox.engine_socket`, `storage.data_dir`, `hf.cache_dir` and `daemon.listen`. `settings.set` refuses them, and any key under them, to every principal but the owner with `RRS-C1005` (scope shown as owner, path `#/key`), at either level and in a dry run, so a `system.admin` token or a plugin can't turn itself into the owner's code at a later step.
