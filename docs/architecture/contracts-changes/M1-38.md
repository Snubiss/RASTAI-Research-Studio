- **M1-38:** `rastai_train`'s loop, optimizer, checkpoints, resume contract and classification recipe (python layout 5; training-evaluation flows 4.1, 4.3, 5.1 and 5.2; ADR-0024). `rastai_train` loses its (M1) marker in 2.2 and 15.2, and 15.2 registers the code names under it; the names of later build steps carry their own (M5) markers (`recipe_availability`, `capability.py`, `export_checkpoint`, `kl_divergence`, `distributed.py`, `kernels/four_bit_linear.py`). No wire, document, command, event or catalog shape changes: resume.json is `rastai.resume/1` as it stands, checkpoint.saved is the existing event, and every code used is already in 10.3 (`RRS-T0003`, `RRS-T0005`, `RRS-T2001`, `RRS-T2002`, `RRS-T2004`, `RRS-T2005`, `RRS-T3001`, and `RRS-D1001` for a dataset file that isn't `.jsonl` or `.csv`). `rastai_plugin`'s `TrainingContext` and `Batch` get the fields M1-37 left to this task (15.2's plain types of `types.py`): `TrainingContext` has `run_id`, `run_folder`, `model`, `device`, `optimizer`, `loader`, `validation_examples`, `dataset_hash`, `split`, `settings` and `progress` (torch objects typed `Any`, since only `NodeType`, `Lens` and `Sampler` may name torch there), and `Batch` has `examples`, the loader's examples in epoch order. Choices for the owner's review: `build_training_context` takes `TrainStartArgs`, the run id and folder, `TrainingSettings` and the device instead of python layout 5.2's `(arguments, launch: WorkerLaunch, host)`, because `WorkerLaunch` is `rastai_worker`'s and `rastai_train` may not import it (2.2); the train job (M1-46) turns job.json into those values. `write_checkpoint` takes the step's `validation_loss` instead of `is_best` and writes it into `weights.safetensors`' `__metadata__` (`validation_loss`), so a resumed job finds its best checkpoint again (`resume_from_latest_checkpoint`) without a file 8.4 doesn't list. The loop applies the retention rule after each save (`remove_unkept_checkpoints`: the newest `keep_last`, the best and `CheckpointPolicy.pinned_steps`), so a run's disk stays at keep_last + best + one in progress, the estimate of platform flow 8.1; the daemon's GC still removes leftover `.partial` folders and the rows of folders that are gone. `load_resume_state` returns a `ResumePoint` (the recipe state and the RNG tensors, restored by the loop after `recipe.prepare`, before the first batch) instead of a dict. A checkpoint whose files the wheel refuses is `RRS-T2002` and `resume_from_latest_checkpoint` tries the next older one, naming each in `ResumePoint.damaged_checkpoints` for the job to report; one of another run, dataset, split, schedule, design or label set is `RRS-T2005` at once; none left is `RRS-T2004`. `checkpoint.saved`'s `checkpoint_id` is a new 8.6 id made by `new_generated_id` (48-bit millisecond time and 80 random bits in Crockford base32, the layout of `rastai-core`'s `new_id`, so ids still sort by time), and `resume.json`'s `id` is a new `doc_` id. The loop writes `run.state_changed running` when it starts and never the final state (the worker's edge does: preempted and exit 75 after SIGTERM); `train.preempted` and `checkpoint.resumed` stay (M5) events, so the loop doesn't emit them yet. A checkpoint that hits a full disk raises `RRS-T2001` with the `.partial` folder removed; the pause of flow 4.2 (the run `paused` with its state in memory) joins with the train job, which has `pause_for_full_disk`'s worker side. Validation runs at every checkpoint when the split has rows (`validation.loss`, `is_best`), with the random generators put back afterwards, so how often checkpoints run never changes the training stream.
- **M1-38 (review round 1):** `CheckpointPolicy` no longer restates the `training.checkpoint` settings: it holds the generated `SettingsCheckpoint` (`checkpoint_settings`, integers as 11.2 types them) beside `every_steps` and `pinned_steps`, which aren't settings, and the new `checkpoint_policy` fills the fields a run's settings leave out with 11.2's defaults (`keep_last` 3, `interval_minutes` 15, `preemption_budget_seconds` 25); `build_training_context` refuses a policy with an unfilled field (`ValueError`). The shape of `JobSpec.checkpoint_policy_json` isn't defined here: it lands with M1-46's contract change. Choice for the owner's review: `TrainingSettings.micro_batch` and `gradient_accumulation` are two values copied from the run's `TrainingPlan`, not a second `TrainingPlan` type, so `TrainingSettings` keeps them as plain integers. `rastai_models` exports `sync_folder` (15.2), which `rastai_train`'s checkpoint write imports from the package. The SIGTERM checkpoint skips the validation pass (no `validation.loss`, never `is_best`), because the preemption budget times only the write. A resume that falls back past damaged newer checkpoints removes them, so the run's latest, best and retention never count a folder newer than its step; the daemon's GC drops their index rows as for any folder that is gone.
