- **M1-22 (contract):** The skeleton's commands. `COMMANDS` gets its first 16 rows, every one `preview` (owner decision N3): `system.status`, `system.shutdown`, `command.list`, `job.list`, `job.get`, `job.cancel`, `train.start`, `settings.get`, `settings.set`, `token.login_code.create`, `token.create`, `token.list`, `token.revoke`, `plugin.list`, `node.list` and `node.status`, so their 6.4 rows lose the (M1) marker. `plugin.list` and `plugin.permissions` (M8) get a row each, so the one marker left can't read as the row's. Their `<Name>Args` and `<Name>Result` types land in rastai-formats' `commands/` with the six parts they share (`JobSummary`, `NodeSummary`, `PluginSummary`, `SettingKeySource`, `TokenSummary`, `TrainingPlan`; 6.5, 15.1), and `just codegen` writes `schemas/commands/`, the JSDoc types, the typed wrappers and the Python dataclasses from them. A command whose handler isn't built yet fails with its area's "not available yet" code (catalog/README.md). `job.cancel`'s row holds `training`, never `read`: the row scope is what keeps a command out of the journal and lets it run during an update's maintenance window, and what a `read`-only token (`mcp-default`) reaches, so a command that ends a job holds a mutating scope; `training` because a training job is M1's only job kind, and its handler also checks the scope of the command that started the job (6.3, 6.4). The task that registers the first job kind started under another scope revisits the row (it is `preview`). The first `secret` result fields (`TokenCreateResult.token`, `TokenLoginCodeCreateResult.code`) bring the rule for them: `secret` and `content` fields of a result are redacted in `result_json` like those of the arguments, and an idempotent replay returns that stored, redacted result, so a retried `token.create` makes no second token and shows `"<redacted>"` in place of the first one's text (5.1, 8.2; flows/platform.md 3.1). Job, node and plugin kinds and states travel as the 9.x names in text, never as a second copy of the proto enums. The closed sets of 6.5 that no proto enum holds (`TrainingPlan.method` and `dtype`, `PluginSummary.source`, `NodeSummary.transport`, `SettingKeySource.source`, `SettingsSetArgs.level`, `TokenCreateArgs.preset`) are enum fields, so the schemas and the generated types limit them. `rastai-core` gains `GLOBAL_FLAGS` (the global flags of the `rastai-cli` row, kept beside the other naming rules so the plugin host can read them too) and `negated_flag_name`, and `command_table.rs` refuses an argument whose flag or off flag is a global one (15.1). `catalog_checks.rs` gains the `fix_command_id` rule of control-plane layout 2.6: a fix button runs a row of the core table, or a 6.4 command marked with the milestone that builds it (`model.download` (M2), `storage.gc` (M5)). `@rastai/client` gets its package and the two JSDoc files the generated wrappers name: `CommandExecutor` and `ExecuteFunction` (`command-executor.js`, as in 12.4), `ExecuteOptions` and `ExecuteOutcome` (`types.js`), so `commands.js` type-checks. The rest of the package is M1-50's, and its names keep their (M1) markers (2.3, 15.3). Two crate edges come with the rows (2.1, control-plane layout 1.1 and 4.10): `rastai-codegen` depends on `rastai-proto`, because a row's kind and stability are the generated enums; and `rastai-formats` takes `rastai-core` as a dev-dependency only, for `tests/commands_described.rs`, so its library still depends on `rastai-diag` alone.
