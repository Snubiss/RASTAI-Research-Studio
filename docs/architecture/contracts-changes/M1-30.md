- **M1-30:** `rastai-server`'s `POST /mcp` (`http/mcp_endpoint.rs`). 15.1 registers `handle_mcp_post` and `McpHttpReply` (the layout 7.3 sketch's handler and its plain-data answer) and the `Server` field `mcp_sessions` (layout 8.2). MCP runs as the bearer token's principal on both listeners: daemon.sock admits its own user as the owner, but the `rastai mcp` bridge reaches `/mcp` over it with a scoped token, so the endpoint takes its principal from the token through the gate's own bearer check (`RRS-C1002` without one, `RRS-C1006` for a revoked one) and never falls back to the owner (flows/platform.md 4.3). Sessions follow MCP's Streamable HTTP rules as the bridge expects them: `initialize` opens one and answers its id in `Mcp-Session-Id`; any other message without the header is 400, and one naming a session the daemon doesn't hold (restarted, idle for 24 h, or opened by another token) is 404; notifications and client replies are 202 with no body; an unsupported `MCP-Protocol-Version` or a body that isn't a JSON-RPC message is 400 with `RRS-C3001`; `GET /mcp` is 405. At most 256 sessions are kept, the least recently used making room. The route takes bodies up to `MAX_MESSAGE_BYTES`, the bridge's own cap, rather than axum's 2 MiB default. No wire, document or command shape changes.
