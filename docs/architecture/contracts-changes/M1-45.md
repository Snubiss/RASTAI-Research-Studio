- **M1-45:** `rastai-node` reattaches to its jobs after a restart and sends heartbeats. No wire, document or command shape changes: `Heartbeat` and `HeartbeatRequest` (4.4), the `lost` job state and its transitions (9.1) and the reattach codes `RRS-J3002`, `RRS-J3003` and `RRS-J3006` (10.3) are used as they stand. 15.1 registers the names the code adds and drops the (M1) markers it builds: in `jobs/reattach.rs`, `reattach_jobs` and `HOST_RECONNECT_TIMEOUT_SECONDS` (15.10 now names `rastai-node` as an owner beside `rastai_worker`: the node waits as long as the worker retries); in `heartbeat.rs` and `hub_client.rs`, `start_heartbeat_loop`, `HeartbeatLoop`, `request_heartbeat`, `build_heartbeat`, `send_heartbeat` and `HubConnection` (its (M1) marker dropped); in the job files, `recorded_process`, `is_running_process`, `classify_vanished` and `VanishedFacts`; the files `jobs/reattach.rs`, `heartbeat.rs` and `hub_client.rs`; and in `rastai-core`, `job_spec_from_json` (its (M1) marker dropped), which reads `job.json`'s `job_spec` back on reattach. `JobOptions` gains the reconnect timeout, so tests shorten the 300 s. 15.9 adds the tests-only `RASTAI_TEST_NODE_FOLDER`: `crates/rastai-node/tests/reattach.rs` starts its own test binary again with it set, which runs only a node in that folder, so the kill -9 tests can SIGKILL a node process mid-run. Rules the code now keeps, recorded in node layout 7.3 to 7.5 and platform flow 2.3: a `job.json` names a live process only when that pid leads its own process group (every worker does, through `setsid`) and has not exited, besides the boot id and start ticks, so a file naming a member of another group never makes the node signal that group; a reattached job whose process is gone takes its end from its last `run.state_changed`, except when it left no record of its own in the log, didn't register with the restarted node, and the run's `stderr.log` ends with the `RRS-J3006` refusal (exit 5): it then fails with `RRS-J3006` and takes nothing from the other writer's frames (the exit-5 edge noted on #199). `stderr.log` is the run's and `job.json` doesn't record where a job's part of it starts, so the refusal line counts only for a job that can't have opened the log (the worker opens it before `Register`); a job that completed after an earlier job's refusal still succeeds, and a job that left nothing at all after one fails with `RRS-J3006` rather than `RRS-J3002`. A gone job's terminal `job.json` is the one read back with its final state, so it keeps its pid, boot id and hardware; `reattach_jobs` runs before `worker-host.sock` is served, so a worker that registers the moment the socket appears always finds its job (a `Register` for an unknown job is refused, and the worker takes a refusal as final); and a finished run's tail positions are forgotten, when its job ends and when a watch ends having seen the writer gone (M1-44 kept them for the node's life). Heartbeats go every `nodes.heartbeat_seconds` and at once, coalesced to one per 100 ms, on every job state change and on a new daemon session. Not yet: the session token on `NodeHubService` calls (its metadata key is a wire name, which lands with the daemon's node link, node layout 7.9), leases restored from `granted_leases` (M3), and sandboxes adopted after reattach (M5).
