- **M1-43 (contract):** The job token's metadata key, a code for an undelivered signal, and the node's own `job.json` fields. The job token travels in gRPC metadata between a worker and its node (3.2, 4.5), but no key was named, and a metadata key is a wire name: it is now `rastai-job-token`, carrying the 64 lowercase hex characters of `RASTAI_JOB_TOKEN`. The worker sends it on every `WorkerHostService` call (`Register` first) and the node on every `WorkerService` call (`Hello`, `Control`); `job.json` `job_token_hash` is `hash_bytes` of those characters (`blake3:<64 hex>`, 8.6). `SignalJobResponse` carries a `Diagnostic` "why the node didn't deliver the signal", and no code covered that: `RRS-J0004` joins the lifecycle range, 0001–0999 (10.3; the catalog's withdrawn draft `RRS-J0003` stays unused): no such job, a job that has ended, no signal named, a `Control` value (`PAUSE`, `RESUME`, `CHECKPOINT_NOW`, `STEP`) before the worker registered, or a failed `Control` call or `kill` tool. A worker's own refusal comes back as its `ControlResponse.diagnostic` (4.4). 8.4's `job.json` fields gain the node's own `job_id`, `run_id`, `kind`, `state` and `started_unix_ms`, which node layout 7.4 step 3 already listed, and `final_state` is spelled as `job_state_name` writes it (empty while the job is live). The node layout names the code (7.4 signals, 11.1) and the key (7.4 step 2). Left open for the heartbeat task (M1-45): `JobInfo` has no field for a terminal state's reason (`preempted` after exit 75, 9.1), so a daemon that builds `job.state_changed` from heartbeats can only read it from `exit_code` 75; a `JobInfo.reason` field would be its own contract PR.
