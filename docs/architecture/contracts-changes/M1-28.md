- **M1-28:** The bus, `EventService.Subscribe`, the daemon's own event log and the run tails. 15.1 registers the names the code adds and drops the (M1) markers it builds: in `rastai-server`, the `Server` fields `bus`, `daemon_log` and `tailed_run_ids`; `events/bus.rs` (`Bus`, `BusFilter`, `new_bus`, `publish`, `events_after`, `subscribe`, `event_matches`, `bus_event_from_record`, `BUS_BUFFER_EVENTS`); `events/daemon_events.rs` (`record_daemon_event`, losing its marker, `DaemonLog`, `new_daemon_log`, `DaemonLogSegment`, `daemon_log_segments`, `daemon_log_name`, `DAEMON_LOG_SEGMENT_BYTES`, `DAEMON_SOURCE`); `indexing/run_tail.rs` (`RunEventSource`, `tail_run`, `start_run_tails`) and `indexing/daemon_log_replay.rs` (`replay_daemon_log`); `http/event_endpoint.rs`; and `wait_until_stopping` (`shutdown.rs`). In `rastai-store`, `append_raw_frame` loses its marker: it appends one whole frame another writer made, as it is, and refuses one whose sequence isn't the log's next (`RRS-S2003`) or that isn't a whole version-1 frame (`RRS-S3005`, nothing written). `INDEX_BATCH_RECORDS`, `INDEX_BATCH_MS`, `INDEX_DISK_FULL_RETRY_SECONDS` and `NODE_RECONNECT_BACKOFF_SECONDS` keep their 15.10 values.
- **M1-28:** How the pieces behave, within what 7.1, 7.2 and flows/platform.md 6.1–6.3 already say. The bus gives each event the next `bus_sequence` (the first after a start is the start time in ms × 1,000) and keeps the last `daemon.bus_buffer_events` (10,000). `Subscribe` is `application/connect+proto` only (layout 11.3; anything else is 415 with `Accept-Post`); `after_bus_sequence` 0 is a new stream that starts with the next event, as `SubscribeRequest`'s comment says; a gap no longer all in the buffer, or a sequence this daemon never gave out (it restarted since), ends the stream at once with `RRS-C0401` in the end-of-stream envelope. A scoped token needs `read` to subscribe (`RRS-C1005`, naming `EventService.Subscribe`), and the events that carry conversation content (`chat.token`, `conversation.changed`, `psychology.packet`, `gym.peek_step`) reach only a caller with `conversations.read`, as for a plugin iframe (frontend layout 10.5). A token revoked while its stream is open ends it with `RRS-C1006` within a second (flows/platform.md 4.3; M1-27 handed this over), a subscriber more than 1,024 events behind is ended with `RRS-C0401` and resumes from the buffer, and a stopping daemon ends every stream cleanly so its listeners can finish. `ListEventTypes` is not served yet: it joins with the event-type table (`events/event_types.rs`).
- **M1-28:** The daemon's own log. `record_daemon_event` appends to `<data>/daemon/events.log` with an fsync, indexes with `ApplyDaemonEvents`, then publishes, all under one lock so records are indexed in log order; a record whose index write failed is sent again with the next one, so the cursor never moves past it, and every record of the batch that commits is published. Each segment's cursor is `log_cursors` row `daemon:<n>`, its number counted from 1 when it is started, so the name survives the roll: the live file is the rolled segments plus 1. At 256 MiB, or when the live file can't be appended to (a corrupt frame or a sequence gap), it is renamed `events-<n>.log` and a new one started. At startup `replay_daemon_log` indexes every segment's records after its cursor before the listener opens. A replayed `command.finished` writes its outcome over the journal row, so a command whose record reached the log keeps its real outcome whether or not its row was closed with `RRS-C0005` first. `execute_command` now records `command.finished` for every journaled command (M1-27 handed this over), after its finished journal row.
- **M1-28:** The run tails. `tail_run` watches a run after `runs.acked_sequence` and handles batches of up to 256 records or 100 ms: for a remote run (`RunEventSource::is_remote`) it appends them to the daemon mirror with `append_raw_frame` and syncs (the frames are encoded again from the decoded records, so the mirror holds the node's records but not always its bytes: prost drops a field this build doesn't know; flows/platform.md 6.1's "the same bytes" holds for every field this build knows), then indexes them with the ack in one transaction, then publishes them (`job:<job_id>`, or `node:<node_id>` for a record without a job). After a restart a remote run's mirror records after the ack are indexed first and the node is asked only for what follows the mirror. The node's report (sequence 0) is published and ends the tail, never mirrored, indexed or acknowledged; a refused record (`RRS-S2004`) gets the records before it indexed, is published as `diagnostic.reported` about the run, and ends the tail; a full disk (`RRS-S3002`) is published once and retried every 10 s; a broken stream is watched again by the tail itself after 1 s, doubling to 30 s, and the tail ends when the node ends the stream (4.4), not on a run state. A tail holds its run in `Server.tailed_run_ids` until it ends, and `tail_run` returns at once for a run that already has one. `start_run_tails` tails every run on a node whose state doesn't end it and that has no live tail; the node links (M1-47) call it after every connect and reconnect and implement `RunEventSource` over `NodeService.WatchRunEvents`. Layout 13.1 says so (its diagram had the node link re-watch and the tail stop on a terminal state). `Subscribe`'s streamed body is `ChannelBody` in `http/connect.rs`, an `axum::body::HttpBody` over the channel; its frame type comes from `http-body`, axum's own body crate, which 2.5, 2.1 and spec §27 now list with `http/connect.rs` as its one file (`check-imports`), so `rastai-server` has no tonic until M1-47. No new codes, commands, events, tables or settings, and no shape change.
