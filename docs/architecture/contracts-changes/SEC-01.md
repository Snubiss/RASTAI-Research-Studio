- **SEC-01 (contract):** Tokens record their creator, so revocation follows what a principal made (threat model R28, issue #230; the owner decided on 2026-10-12 to fix it in M1). Before this, a token or plugin holding `system.admin` could make another `system.admin` token, and revoking it left that successor live. 8.2's `tokens` gains `created_by` (M1): the principal that ran `token.create`, as `principal_label` writes it in `command_journal.principal` (6.3): `owner`, `token:<token_id>` or `plugin:<plugin_id>`, the owner narrowed by `acting_plugin_id` included. 8.2 gains "Token creators and revocation". `token.revoke` revokes, in the same write transaction and with the same `revoked_unix_ms`, every live token whose `created_by` chain leads to the revoked one; once that commits, each is marked revoked in the gate's cache and gets `RRS-C1006`. Revoking a token already revoked still sweeps the live tokens under it. A plugin that becomes `disabled` (`disable_plugin`, which `plugin.disable` (M8) calls) or `uninstalled` (M8) revokes the tokens whose chain leads to it, in the same write transaction that saves its `plugins` row, or in a transaction of its own for a dev plugin, which has no row. `token.create` writes its row only while its creator is live: a `token:` creator is checked in the writer transaction that inserts the row (`RRS-C1006` when revoked); a `plugin:` creator is checked against the plugin host's state under one plugin-host lock, which the create holds until its insert commits and a disable or uninstall holds until its cascade commits and is in the cache (`RRS-C1005` when the plugin isn't `enabled`). So a dev plugin is checked like any other, and a create racing a revoke can't leave a successor behind. `token.create` adds its cache entry before it sends its insert and removes it if the insert fails or is refused, so a cascade that commits after the insert always finds the entry to mark and no create puts a live entry back. After the plugins load and before the HTTP listener opens, the daemon revokes the live tokens whose chain leads to a plugin the host holds no plugin for, or holds as `disabled`: this is how dropping a dev path (owner-only, read at start) revokes that plugin's tokens, and it also covers an `uninstalled` row, a folder removed by hand and a disable cut short by a crash. The owner is never revoked, so a chain is followed only through `token:` and `plugin:` creators. A plugin installed from M8 by a token holding `plugins.manage` chains to `plugin:<plugin_id>`, not to that token; M8-E02 (#136) decides how an install records who asked for it. Migration `0003` (`0003_token_creator.sql`, the next free number on `main`) is plain SQL: it adds the column as `TEXT NOT NULL DEFAULT ''`, fills existing rows with `json_extract` from the `principal` of the successful `token.create` journal row whose `result_json` names the token (the id isn't `secret`), and with a recursive common table expression revokes, at the migration's time, every live token whose filled-in chain leads to a revoked token or a `disabled` or `uninstalled` plugin; `crates/rastai-store/tests/index_migrations.rs` tests it. `TokenSummary` (6.5, `crates/rastai-formats/src/commands/token.rs`) gains `created_by`, a required string, so `token.list` shows each token's creator; `just codegen` regenerates `schemas/commands/rastai.command.token.list/1.json`, the JSDoc type and the Python dataclass (`token.list` is `preview`, so the newly required field passes `check-schema-diff` with this entry). Until the code PR lands, the handler answers `created_by` with the empty text, as for a token no record names. `crates/rastai-store/tests/index_migrations.rs`, which compares 8.2 with the migrated tables, now reads a column's own milestone marker as `check-names` does (12.6: in a list cell a marker covers only the name it follows), so `created_by` (M1) waits for the code PR's migration. 6.4's `token.*` row, flows/platform.md 4.3 and threat model R28 (now owned by SEC-01) say the same. Choices for the owner's review: `created_by` uses the journal's principal text rather than a bare id, so a token id and a plugin id can't be confused; `TokenRevokeResult` doesn't list the tokens a cascade revoked (`token.list` with `include_revoked` shows them, each with the same `revoked_unix_ms`); a plugin the host moves to `incompatible` or `failed` keeps its tokens, since that isn't the owner's decision and its own principal holds no scope while it isn't enabled; the migration backfills from the journal and revokes already-orphaned successors rather than leaving pre-existing tokens outside the rule; a plugin's liveness comes from the plugin host under a lock rather than from `plugins.state`, because a dev plugin has no row.
