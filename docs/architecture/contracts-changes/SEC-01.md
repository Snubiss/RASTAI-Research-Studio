- **SEC-01 (contract):** Tokens record their creator, so revocation follows what a principal made (threat model R28, issue #230; the owner decided on 2026-10-12 to fix it in M1). Before this, a token or plugin holding `system.admin` could make another `system.admin` token, and revoking it left that successor live. 8.2's `tokens` gains `created_by` (M1): the principal that ran `token.create`, as `principal_label` writes it in `command_journal.principal` (6.3): `owner`, `token:<token_id>` or `plugin:<plugin_id>`, the owner narrowed by `acting_plugin_id` included. 8.2 gains "Token creators and revocation": `token.revoke` revokes, in the same write transaction and with the same `revoked_unix_ms`, every live token whose `created_by` chain leads to the revoked one (each leaves the gate's cache and gets `RRS-C1006`); revoking one already revoked still sweeps the live tokens under it; a plugin that becomes `disabled` (`disable_plugin`, which `plugin.disable` (M8) calls) or `uninstalled` (M8) revokes the tokens whose chain leads to it; `token.create` writes its row only while its creator is live in the same writer transaction (a `token:` creator not revoked, else `RRS-C1006`; a `plugin:` creator `enabled`, else `RRS-C1005`), so a create racing a revoke can't leave a successor behind; the owner is never revoked, so a chain is followed only through `token:` and `plugin:` creators. Migration `0003` (`0003_token_creator.sql`, the next free number on `main`) adds the column as `TEXT NOT NULL DEFAULT ''`, fills existing rows from the `principal` of the successful `token.create` journal row whose `result_json` names the token (the id isn't `secret`), and revokes, at the migration's time, every live token whose filled-in chain leads to a revoked token or a `disabled` plugin. `TokenSummary` (6.5, `crates/rastai-formats/src/commands/token.rs`) gains `created_by`, a required string, so `token.list` shows each token's creator; `just codegen` regenerates `schemas/commands/rastai.command.token.list/1.json`, the JSDoc type and the Python dataclass (`token.list` is `preview`, so the newly required field passes `check-schema-diff` with this entry). Until the code PR lands, the handler answers `created_by` with the empty text, as for a token no record names. `crates/rastai-store/tests/index_migrations.rs`, which compares 8.2 with the migrated tables, now reads a column's own milestone marker as `check-names` does (12.6: in a list cell a marker covers only the name it follows), so `created_by` (M1) waits for the code PR's migration. 6.4's `token.*` row, flows/platform.md 4.3 and threat model R28 (now owned by SEC-01) say the same. Choices for the owner's review: `created_by` uses the journal's principal text rather than a bare id, so a token id and a plugin id can't be confused; `TokenRevokeResult` doesn't list the tokens a cascade revoked (`token.list` with `include_revoked` shows them, each with the same `revoked_unix_ms`); a plugin the host moves to `incompatible` or `failed` keeps its tokens, since that isn't the owner's decision and its own principal holds no scope while it isn't enabled; the migration backfills from the journal and revokes already-orphaned successors rather than leaving pre-existing tokens outside the rule.
