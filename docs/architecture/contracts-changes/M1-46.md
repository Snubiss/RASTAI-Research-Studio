- **M1-46 (contract):** What a `train` job's `JobSpec` carries in its two JSON strings, which no contract named (M1-38 left `checkpoint_policy_json` to this task). 4.4 gains "What a job's `_json` fields hold": a `train` job's `arguments_json` is a new `TrainJobArgs` (6.5, 15.1; `crates/rastai-formats/src/commands/train.rs`, generated into the Python dataclasses and the JSDoc types): `start_arguments` (the `TrainStartArgs` the run was started with), `plan` (the daemon's `TrainingPlan`: micro-batch, accumulation, dtype, GPUs), `max_steps` and `seed`. It shares `train.start`'s schema id, because that command's handler (M1-47) builds it, and it isn't one of the command's arguments or results, so `schemas/commands/` doesn't change. `checkpoint_policy_json` is the run's `training.checkpoint` section (`SettingsCheckpoint`, 11.2) as the daemon resolved it for the job's node, keys left out taking their 11.2 defaults and empty text meaning every default; no new type, because a second copy of that section's shape is what M1-38's review removed. A `train` job whose JSON isn't these shapes fails with `RRS-J2001` before it trains. Python layout 7.3 names both. Choices for the owner's review: `max_steps` and `seed` are `TrainJobArgs` fields, not `TrainingPlan` ones, so `train.start`'s result doesn't change; the recipe's own settings (learning rate, warmup, validation share) join `TrainJobArgs` with recipe settings (M5), and until then the train job uses `TrainingSettings`' defaults.
